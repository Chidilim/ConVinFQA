## Architecture Decision Records (ADRs)

Store significant technical decisions in docs/decisions/.

For decisions involving architecture, data models, APIs, security, dependencies, or major design tradeoffs:

1. Check existing ADRs relevant to the task before recommending a design.
2. Discuss the problem, alternatives, tradeoffs, and recommendation with the user.
3. Do not make the decision on the user's behalf.
4. Ask the user to approve the selected approach.
5. Propose an ADR using docs/decisions/TEMPLATE.md.
6. Ask for approval before writing or updating the ADR file.
7. Assign the next sequential ADR number.
8. Record the user's actual reasoning, not assumptions about their preferences.
9. Update the ADR status as appropriate, only after confirming the milestone.
10. Never silently overwrite an accepted decision. Create a new ADR and mark the previous decision as Superseded when it is replaced.

Keep ADRs concise and focused on why a decision was made.

Do not create ADRs for routine edits, simple bugs, or trivial implementation details.

Approval of an ADR does not authorize code modifications. Obtain separate approval for implementation edits.
